01 · The big picture

Understand what is being built

Your computer sends source files to EAS. Expo’s computers install the dependencies, generate the Android project, and compile an APK.

1 · YOUR PROJECTCode + configurationpackage.json, lockfile, app.json
2 · UPLOADFiles go to EASYour internet is needed here
3 · INSTALLnpm ci --include=devThe lockfile must be consistent
4 · COMPILEGradle builds AndroidNative versions must agree
5 · DOWNLOADYour APKDownload, install, use the app
The first failure

Installation stopped

The lockfile was missing dependencies. EAS could not even reach Android compilation.

The later failure

Compilation stopped

After installation worked, Gradle rejected Reanimated 4.2.2 with React Native 0.86.3. Doctor also found duplicate Screens versions.

Six terms to know

TermPlain-English meaning
Node.jsRuns the JavaScript tools on your computer and on the build server.
npmDownloads packages and records the dependency tree.
DependencyA package your app uses. A transitive dependency is a package used by another package.
Native moduleA library containing Android or iOS code. Its version must work with your React Native version.
Expo SDKA coordinated set of package versions. This project uses SDK 57, targeting React Native 0.86.
EAS / GradleEAS runs the cloud build. Gradle compiles the generated Android project.

05 · Failure at “Install dependencies”

Fix npm ci and missing lockfile entries

This was the first blocker. The cloud build stopped before Gradle started.

What happened

The direct dependencies in package.json looked aligned with Expo. The lockfile still omitted some packages lower in the tree, under optional WebAssembly tooling used by lint dependencies. Direct version checks alone could not detect that.

npm ci installs a frozen tree: it checks the lockfile and refuses to repair missing entries. npm install can resolve dependencies and update the lockfile.

Small example

A dependency of a dependency

Your app declares A. A needs B. A complete lockfile records both A and B. Recording only A does not make installation reproducible.

Expected result: clean installation succeeds only after all required entries are recorded.

Your actual example

The missing @emnapi entries

The optional tooling tree required Core and Runtime entries that were not present in the places npm expected.

Expected result: npm resolves them and npm ci --include=dev passes.

Why the first repair advice was incomplete

The initial npm install --package-lock-only advice did not say to switch npm versions. Local npm 11.6.2 continued to accept the incomplete lockfile. We reproduced the exact remaining EAS error with npm 11.21.0, then used that version to repair it. The cloud’s precise npm version was not established; 11.21.0 is the version we used to reproduce and resolve the failure.

Frozen installation behavior: npm ci reference ↗. Lockfile updates: npm install reference ↗.

If existing node_modules still interferes: repair in a clean temporary folder

This mirrors the repair we performed. It preserves the original lockfile as input, but resolves it without the existing installation folder. Run each line separately. Only copy the new lockfile back after the temporary installation succeeds.

Expected result
The original project keeps its source files and package declarations. The verified lockfile is copied back, and a final clean installation succeeds in the project. repair_dir is a shell variable holding the temporary folder’s path; keep using the same terminal.
Do not manually add the error’s versions to the lockfile

Those packages are transitive dependencies. Let npm place the versions required by the current tree. Our first successful repair added 1.11.3 entries; later deduplication legitimately selected 1.10.0 entries for the revised tree. The test is whether clean installation passes, not whether one old error’s version stays forever.

Prevent the next occurrence

  • Keep package.json and package-lock.json together in version control.
  • Check Node and npm versions before generating the lockfile.
  • Run a real npm ci --include=dev before submitting a build.
  • If only the cloud rejects it, compare npm versions and the uploaded files.
  • Do not delete the lockfile as your first fix: doing so can update many unrelated packages.

08 · Connectivity

Know when internet is required

Cloud compilation happens on Expo’s servers. Your terminal mainly submits the work and watches its progress.

StageDoes your connection need to stay on?Reason
Installing tools / downloading packagesYes, unless everything needed is cached.Files and metadata come from package registries.
Signing setup and project uploadYes.EAS must receive the project and complete setup.
Accepted cloud build / waitingNo.The build continues on Expo’s servers.
Checking status / downloading the APKYes.You reconnect to read logs and receive the file.
Using the installed calculatorNo for its calculations.The inspected calculator code does not make network requests.
EAS --local buildMay still be required.Account checks, remote credentials, and dependency downloads can use the internet.

When you can disconnect from a cloud build

Wait until the project upload has completed and EAS has printed a build link and started waiting for that submitted build. These terminal messages are the useful markers:

You can then turn off your internet, close the terminal, or shut down your computer. The cloud job continues. A disconnected terminal may show a monitoring/network error; use the build page to determine the actual server result. Completion still depends on the build succeeding.

Expected result
After reconnecting, EAS lists your Android builds and their statuses. Open the relevant build’s details to download a successful APK or inspect a failure.

Waiting and resuming status checks: Expo’s build monitoring instructions ↗.

If a package download fails

A timeout means a download did not complete; it does not by itself mean your versions are wrong. Reconnect, then retry the command that failed. npm can reuse successfully cached downloads. Our clean installation passed after retrying a timed-out registry download.

Expected result
With the repaired lockfile and a working connection, installation succeeds. If the same network error repeats, inspect your connection, DNS, proxy, and registry access before changing dependency versions.

Local builds are a separate setup

You can compile on Debian using EAS’s local option, but you must provide Java and the appropriate Android SDK/NDK. That workflow is not automatically fully offline, and it does not keep running if you shut down the machine doing the compilation.

Expected result
When the required local Android tools are installed, the build runs on your machine and copies out the APK. This local toolchain was not configured or tested during our cloud-build repair.

Local build requirements: EAS local build documentation ↗.

09 · Diagnose the right line

Separate failures from nearby warnings

Long logs contain warnings, informational messages, and the error that actually stopped the build.

Message you sawWhat it means hereWhat to do
“Unknown error … Install dependencies”A generic EAS summary.Open that phase. In our case, its real error was npm EUSAGE.
“No environment variables … preview”EAS found no configured variables in those visibility groups.No change was required for this calculator’s reported failures.
“Using .nvmrc: 24”The profile had no explicit Node pin.Informational. Optionally pin the tested Node version as shown above.
“NODE_ENV … was not specified”A config-generation warning in the shown Gradle log.It was not the task that stopped compilation. Fix the failed Reanimated assertion first.
Kotlin / Gradle deprecation warningsSome APIs will need changes in future toolchains.They did not stop the shown build. Keep the SDK toolchain aligned and upgrade deliberately.
“Check that no duplicate dependencies are installed”A real Doctor check failure.Align the native packages, deduplicate, and rerun Doctor.
“assertMinimalReactNativeVersionTask FAILED”The fatal Gradle compatibility failure.Install the SDK-compatible Reanimated / Worklets pair.

A method you can reuse

  1. Open the earliest failed phase.
  2. Find the first concrete error, not only the final “Build failed” summary.
  3. Identify whether it is installation, validation, bundling, or native compilation.
  4. Reproduce the relevant check locally.
  5. Apply a focused fix, rerun that check, then request another build.

If a verification tool itself cannot load configuration

During a restricted diagnostic run, Doctor reported a problem parsing the output of npx expo config --json --full. Retrying with working subprocess and network access resolved that diagnostic failure; it was not the application’s Gradle failure.

Expected result
The executable paths should use the Node/npm environment you selected. Expo config prints JSON. Doctor then lists the individual check results, allowing you to distinguish configuration trouble from a tool/network issue.

For routine pre-build checks, use a working internet connection. Offline dependency validation can be incomplete. In our verification, expo install --check --offline was also rejected as an unsupported flag; the normal command is npx expo install --check.
